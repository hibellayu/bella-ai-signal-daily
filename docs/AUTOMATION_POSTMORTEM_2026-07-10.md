# 2026-07-10 AI 日報空資料覆盤

建立日期：2026-07-10（台北時間）

## 事件摘要

2026-07-10 上午，正式站顯示 7/10 日報已生成，但四個內容區塊皆為 0 則資訊。盤查後確認 GitHub Actions 與 GitHub Pages 皆成功執行，問題不在排程或部署，而在產生器只建立空白日報骨架，尚未接上新聞收集、篩選評分與 AI 產文流程。

## 影響

- 使用者看到最新日期日報，但內容為空，容易誤判為新聞資料不足或網站故障。
- `manifest.latest` 被更新到空日報，導致首頁預設顯示 7/10 空內容。
- 自動化驗收標準不足，只有確認「產生檔案與部署」，未確認「內容品質與數量」。

## 根因

1. 自動化範圍落差：原需求是「每天 7 點自動更新有內容的 AI 日報」，但 MVP 實作只完成「每天產生日報 JSON 骨架」。
2. Definition of Done 不完整：沒有把「至少產出可閱讀內容」「每個 section 不可全空」「來源連結有效」「manifest 不可指向空日報」列為驗收條件。
3. 產文流程未拆成明確任務：新聞抓取、日期過濾、評分排序、AI 解讀、品質檢查、部署告警沒有形成獨立 task inventory。
4. 防呆缺失：當產生器沒有內容時仍寫入日報並更新 `manifest.latest`。
5. 溝通問題：先前把「預留後續新聞抓取與 AI 生成流程」當成 MVP 邊界，但沒有明確提醒使用者這代表隔天只會生成空骨架。

## 已採取修正

- 補上 2026-07-10 正式日報內容。
- 更新 `manifest.json` 的 7/10 摘要。
- 在 `scripts/generate_daily_digest.py` 加入防呆：若產生器沒有任何 section items，則不寫入新日報、不更新 manifest，避免空日報上線。

## 第 3 階段：正式自動化何時處理

建議在 2026-07-10 完成緊急修補後，立即進入第 3 階段設計與實作。此階段不應被視為小修，而是一個完整自動化子專案。

建議時程：

1. Phase 3A：資料來源與收集器，0.5-1 天。
   - 建立來源清單與抓取方式。
   - 台灣媒體依台北時間前一日，國際媒體依來源發布日期。
   - 輸出 raw articles JSON。
2. Phase 3B：篩選與評分器，0.5 天。
   - 套用收錄規則與排序規則。
   - 過濾不相關、重複、低價值內容。
3. Phase 3C：AI 產文與品質檢查，1 天。
   - 產出 summary、analysis、What / So What / Now What、applications。
   - 檢查每則來源、日期、連結、字數、語氣與策略深度。
4. Phase 3D：部署與告警，0.5 天。
   - 若無內容或來源抓取失敗，不更新 latest。
   - 產生日誌與通知，讓使用者知道是成功、部分成功或失敗。

保守估計：2-3 個工作階段可完成可用版本；若要提高來源品質與穩定性，建議預留 3-5 個工作階段。

## 未來專案檢查清單

- 自動化需求不可只問「會不會排程」，要問「排程後產物是否達到使用者可用狀態」。
- PRD 必須列出自動化 Definition of Done。
- 空資料、API 失敗、來源無法讀取、AI 生成失敗都要有 fallback。
- `manifest.latest` 只能指向通過品質檢查的資料。
- 每次自動化部署後要有最小驗收：資料檔存在、內容數量達標、來源連結有效、前台讀得到。
- 任何 MVP 若只完成骨架，必須在交付時明確標註「不能產生正式內容」。

## 給 Bella-Agent / LifeOS 的流程提醒

遇到中大型自動化需求時，應遵循 `VIBE_CODING.md` 流程，至少產出：

- PRD：使用者真正期待的完成狀態。
- SDD：系統如何從資料來源到前台顯示。
- Spec：資料格式、API、排程、錯誤處理。
- Task Inventory：拆出可驗收任務。
- Atomic Task：逐步實作與驗收。

本次事件的核心教訓：使用者要的是「每天可閱讀的 AI 日報」，不是「每天新增一個日期檔案」。未來所有自動化都必須以最終使用價值驗收。
